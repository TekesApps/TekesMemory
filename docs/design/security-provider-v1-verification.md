## Transport fixture acceptance repair (2026-11-13)

The two initialization failures were investigated separately from the earlier serial rerun. Both affected mocks set their listener nonblocking, then used accepted streams as if `set_read_timeout(50ms)` made them blocking. On this macOS host, accepted streams inherited `O_NONBLOCK`: observed `F_GETFL=6`, including `O_NONBLOCK=4`. A partial request therefore produced immediate errno 35 / WouldBlock, rather than waiting up to 50 ms. The mock discarded that connection; the client reported `hyper::Error(IncompleteMessage)`, `context: send initialize request`, then the public `unavailable` error.

Controlled causal evidence used the actual two client tests and their shared mock read path. A temporary loopback proxy split each request after its first byte and sent the remainder 20 ms later, below the unchanged 50 ms socket timeout and 900 ms / 2 s client budgets. Both tests failed in `Client::open`, with the one-byte/WouldBlock/IncompleteMessage chain. Adding only `set_nonblocking(false)` in the shared reader made both pass under the same proxy. The permanent regression sends complete headers followed by the body 20 ms later and explicitly marks the accepted socket nonblocking, so it covers macOS inheritance on other platforms as well. It failed before the fix and passes afterward. This proves a concrete fixture defect and its causal failure mode; the original failure log lacked syscall traces, so the exact original packet/scheduling order is not claimed known.

The final change is confined to `tests/transport_contract.rs` and this verification note. The duplicated mock readers share one implementation that explicitly restores blocking mode. No client deadline, socket timeout, DELETE acknowledgement delay, retry assertion, or bounded-close assertion was widened or removed. Temporary runtime diagnostics and proxy hooks were removed. All 22 runtime source/configuration/Cargo files match the original frozen manifest; `src/client.rs` retains SHA256 `fc81801794ff963cb1512ab8624e3179444ed1b2c8348a9b9881a8e6d49c1984`. Diagnostic builds did relink the executable, so its new binary identity is separately recorded and is not represented as the old binary's integration evidence.

A separate diagnostic signature must not be conflated with the initialization defect: `/tmp/memory13-native-repeat/run-2.log` through `run-6.log` recorded five `client_drop_waits_for_bounded_session_delete_ack` failures at the acknowledgement assertion (`ack_at_return=0`, expected 1), after successful initialization. These runs included temporary per-connection diagnostic printing and did not capture a sufficient timing trace to attribute the acknowledgement failure to the nonblocking defect or to prove a runtime close defect. It did not recur in the final ordinary parallel transport run or full suite. At that stage the causal uncertainty was retained; the later exact-diagnostic reconstruction below resolves the reproduced mechanism. No close-budget workaround was introduced.


Follow-up bounded diagnosis used in-memory timestamps and emitted each timeline only after the test completed, without per-connection printing. `/tmp/memory13-ack-timeline/report.json` preserves eight parallel observations: four with the fixed fixture and four with the original nonblocking fixture. All eight observed entry into the mock DELETE handler, then its flag marking completion of the intended processing delay, then `cancel` return, `closed` notification and Drop return, in that order. That flag is set before writing the HTTP response; it is not an independent observation that the client received the response. Drop elapsed times were 36.689–47.521 ms; none captured return before the mock processing-completion flag or exhaustion of the 100 ms close wait. The additional acknowledgement failure did not reproduce in this bounded batch. These successful observations do **not** establish the cause of the five earlier diagnostic failures or prove that they are resolved.

Inspection of locked rmcp 3.5.1 confirms `cancel` awaits the service task, which awaits transport close, which awaits the HTTP worker and its DELETE attempt. This waits for that attempt to terminate; a network failure or the SDK's cleanup timeout can also terminate it, so a successful `cancel` return alone is not proof of successful remote acknowledgement. The temporary instrumentation was removed, and all frozen source files and the binary were restored and hash-verified before downstream acceptance resumed. No production implementation, client timeout, close budget or assertion was changed by this follow-up diagnosis.


### Exact reconstruction resolves the diagnostic acknowledgement failures

Reconstructing the temporary code and command that produced `/tmp/memory13-native-repeat/run-2.log` through `run-6.log` reproduced the acknowledgement-flag failure twice. The cause is synchronous per-connection `eprintln!` diagnostics inserted on the mock server's request-processing path consuming the existing 100 ms Drop wait. It is a diagnostic observer effect, not evidence that `rmcp cancel` returned before its cleanup attempt. The logs measure time spent in the synchronous printing sections; they do not establish whether that time was formatting, a stderr lock, output I/O or scheduling, and no TTY/filesystem explanation is asserted.

Evidence:

| Trace | Drop elapsed | Flag at Drop return | Observation |
| --- | --- | --- | --- |
| `/tmp/memory13-ack-exact-reconstruction-1.log` | 103.669 ms | 0 | `drop_wait_timeout`; mock processing-completion marker occurred afterward |
| `/tmp/memory13-ack-print-phases.log` | 105.037 ms | 0 | Detailed failure timeline below; `cancel` completed after response writing |
| `/tmp/memory13-ack-print-A1.log` | 92.225 ms | 1 | Printing enabled; substantial diagnostic delay, below the failure threshold this time |
| `/tmp/memory13-ack-print-B.log` | 40.718 ms | 1 | Same `fcntl` observations retained, per-connection printing suppressed |
| `/tmp/memory13-ack-print-A2.log` | 84.085 ms | 1 | Printing restored; substantial delay returned |

A1/B/A2 is a delay ablation comparison, **not** a red/green/red sequence: both A comparison runs passed. The two preceding complete failure traces establish the threshold-crossing failure. `fcntl(F_GETFL)` took 0–8 microseconds in the ablation traces, while enabled printing sections took milliseconds; suppressing printing removed that delay without removing the flags reads or changing any timeout/ack assertion.

The detailed failure trace has a single monotonic clock origin. Drop started at 79.143 ms; the DELETE frame was already fully read at 121.878 ms. The next method-diagnostic print ran from 121.882 to 152.581 ms. The event labelled `delete_received` was recorded **after that print**, at 152.581 ms: it denotes entry into the mock DELETE handler/counter, not network arrival. The printing sections while Drop was waiting totalled approximately 67.956 ms. Drop's 100 ms timed wait returned with timeout at 184.172 ms, and Drop returned at 184.177 ms. The mock's processing-completion flag was set at 185.863 ms, before its HTTP write; `response_write_end` followed at 185.896 ms, `cancel_return_ok` at 186.342 ms, and `closed_send` at 186.350 ms. Thus the observed failure is budget exhaustion while diagnostics delay server processing, not cleanup completing early. This ordering supports the awaited cleanup chain, but neither the mock flag nor `cancel Ok` alone independently proves successful remote deletion/HTTP acknowledgement.

Reproduction used `MEMORY_TRANSPORT_DIAG=1 cargo test --locked --test transport_contract -- --nocapture`. Exact-reconstruction runs used shell redirection `> /tmp/<log> 2>&1`. A1/B/A2 used Python `subprocess.run` with a regular log file passed as `stdout` and `stderr=subprocess.STDOUT`; B additionally set `MEMORY_DIAG_SUPPRESS_PRINT=1`, while A1/A2 left it unset. There was no `tee` or tool PTY. The controlled code is preserved at `/tmp/memory13-ack-print-ab-client.rs` and `/tmp/memory13-ack-print-ab-tests.rs`; `/tmp/memory13-reconstruct-failed-diagnostics.py` records the reconstruction of the earlier diagnostic edits. `/tmp/memory13-ack-rootcause-report.json` retains the parsed raw timelines and event semantics. The historical five runs lacked these timestamps, so their exact elapsed times are not invented; the same diagnostic code and signature now have a reproduced, measured cause.

No additional product fix is warranted by this result: those temporary synchronous prints were already absent from the frozen candidate. All temporary code was removed again, the original binary bytes restored, and all runtime source/Cargo/schema hashes retained. The existing blocking-socket fixture fix remains; the 50 ms socket timeout, 100 ms Drop wait, 30 ms mock processing delay and all business assertions remain unchanged. Final related verification: `cargo test --locked --test transport_contract` **13 passed**, `/tmp/memory13-ack-rootcause-final-parallel.log`. Already-passing full-suite and cross-repository evidence is reused for unchanged runtime code/artifacts; no further full-suite or cross-repository rerun was performed for this documentation-only follow-up.
